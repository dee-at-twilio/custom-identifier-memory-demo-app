Composite-Key Memory — Architecture Differentiation
With jobID as unique identifier

jobID is the identifier, phone is a trait.

The custom jobID identifier (enforceUnique: true) creates one profile per job. The tech's phone number lives as a trait — so Memory can't answer "which profiles belong to this phone?" on its own. The app carries a tiny external index for that one lookup.

jobID identifier + external phone→jobIDs index

Twilio Memory is still the source of truth for job data. The external index carries only one column of information: phone → profileIds.

With jobID as unique identifier

Available today — with one caveat you own.

Job isolation is still a Memory primitive
One profile per job, keyed by the custom jobID identifier. Observations and summaries scope naturally; Recall returns one job's history at a time. CINTEL summaries still land on the right profile automatically because the participant carries its profileId.
One tiny external table — phone → [profileIds]
Because mobile is a trait, not an identifier, Memory can't answer "which profiles belong to this phone?" A JSON file, a Redis hash, or a two-column SQL table is enough. Written on assign, read on inbound SMS.
Multiple active jobs per tech, by design
Nothing prevents a technician from having several concurrent active jobs. Conversations for each live under distinct channelIds. Inbound SMS routing disambiguates in the app: if only one active exists, route it; otherwise, reply asking the tech to prefix the message with the Job ID.
Available on GA Memory — no gated features
No phone AND jobID matching rule needed. Standard identifier config plus one custom identifier with enforceUnique: true. Ships today.
The caveat: routing is a two-hop lookup
Every inbound SMS costs one external-index read plus N Memory GETs (one per profile the tech has ever held). Composite keys fold this into a single Twilio call; here, the app carries it. Small, but real — and worth budgeting for at scale.
Two systems, but the split is boring
Unlike the phone-only architecture (where Memory becomes redundant and the DB owns job identity), here the external store only holds a phone→profileIds map. Everything semantic — status, timestamps, conversation wiring, observations, summaries — stays in Memory.
Sequence · Assign new job · jobID identifier

One extra hop for the phone index — the rest is Twilio.

The uniqueness guardrail is gone; multiple active jobs per tech are allowed. state.py owns the phone → [profileIds] map (a JSON file); Twilio Memory owns everything semantic about the job.
